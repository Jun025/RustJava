# 2026-09-16 — 상수풀 태그 15~18 파싱: 「파손」을 「미지원」으로

티켓 `rustjava-cp-tags-15-18-parse-and-honest-diagnosis`.

## 무엇이 바뀌었나

javac 9+ 가 낸 클래스를 읽었을 때 사용자가 보는 문장이 바뀌었다. **그것이 전부다** —
`invokedynamic` 은 여전히 실행되지 않는다.

| | 메시지 |
|---|---|
| 전 | `java.lang.ClassFormatError: Invalid class file` |
| 후 | `java.lang.UnsupportedOperationException: Unsupported class file feature: invokedynamic` |

픽스처 `test-data/indy/StringConcat.class` = `System.out.println("a" + args.length);` 한 줄
(`javac --release 21` · major 65 = 기존 픽스처와 동일). javac 9+ 는 문자열 `+` 를
`StringConcatFactory#makeConcatWithConstants` 호출사이트로 낮추므로 **평범한 한 줄**이
상수풀에 태그 15(MethodHandle)·18(InvokeDynamic)을 넣는다.

## ★티켓 ① 의 범위가 «한 칸 모자랐다» — 이 회차의 가장 값진 실측

티켓 ①은 급소를 **`classfile/src/constant_pool.rs` 의 태그 분기**로만 지목했다.
그것만으로는 **메시지가 바뀌지 않는다.**

`classfile/src/opcode.rs` 의 `0xba` 분기가
`map_res((be_u16, be_u16), |_| Err(()))` 로 ★**opcode 파싱 단계에서 무조건 실패**하고 있었고,
그 실패는 `Code` 속성 파싱 실패 → 클래스 파싱 실패 → **`Malformed`** 로 그대로 이어진다.

개악 M3 이 그것을 그 자리에서 보여준다 — **태그 15~18 을 전부 살려 둔 채** `0xba` 분기만
옛 판본으로 되돌리면 픽스처는 다시 `ClassFormatError: Invalid class file` 로 죽는다.

⇒ 「파손 → 거부」 칸을 여는 데 필요한 파서 수정은 **둘**이고, 티켓은 **하나**를 적었다.
분할 판단(「거부 → 지원」 앞에 칸이 하나 더 있다」)은 **옳고**, 그 칸의 **내용**이 한 항목 넓었다.

## ★`todo!()` 는 «도달하지 않는다» — 측정했다

`jvm-bytecode/src/interpreter.rs:631` 의 `todo!()` 는 무접촉이고, 도달하지 않는다.
「안 부르니까 안 닿는다」로 끝내지 않고 **verifier 를 일시로 꺼서** 잰 결과:

| 실험 | 결과 |
|---|---|
| 현 트리 | `UnsupportedOperationException` (게스트 예외) |
| verifier 의 `Opcode::Invokedynamic(_)` 분기만 제거 (M4) | ★`panicked at jvm-bytecode/src/interpreter.rs:631: not yet implemented` (호스트 abort) |

⇒ 그 `todo!()` 와 픽스처 사이에 서 있는 것은 **정확히 verifier 한 줄**이고, 그것이 서 있다.
유일한 바이트→클래스 진입점 `ClassDefinitionImpl::from_classfile` 이 두 번째 문장에서
`verifier::verify` 를 부르므로 우회로가 없다.

## 대가 — 「아무 태그나 통과」시키지 않았다

`parse_tagged` 의 `_ =>` 분기는 그대로다. 미지 태그는 여전히 파손으로 끊는다.
`validate_constant_pool` 에도 새 태그 3종의 정합성 검사를 넣었다(JVMS 4.4.8):
reference kind ↔ 참조 종류 대응 · MethodType 의 descriptor 가 실제 메서드 서술자인지 ·
Dynamic/InvokeDynamic 의 `name_and_type_index` 가 NameAndType 을 가리키는지.

기존 회귀 테스트 `test_unsupported_constant_pool_tag_raises_class_format_error` 는
★**태그 18 을 「미지원 태그」의 사례로 쓰고 있었다** — 이 회차가 그것을 지원하게 만들었으므로
**13·14·19 세 태그로 바꿔** 같은 단언을 유지했다. 파서 단위로도
`tags_outside_the_accepted_set_are_still_rejected` 가 8개 태그를 민다.

## 하지 않은 것

- **`BootstrapMethods` 속성 파싱 0** — 이미 `AttributeInfo::BootstrapMethods(Vec<u8>)` 로
  받아만 두고 있었고, 그 인덱스를 **역참조하는 코드가 이 회차에 없다**(verifier 가 클래스
  정의 시점에 끊으므로 링크 자체가 일어나지 않는다). 파싱해도 오늘 쓰는 곳이 0이다.
  `ConstantPoolReference::InvokeDynamic` 이 인덱스를 **원문 그대로** 들고 있어,
  링크 회차가 파서를 다시 고치지 않고 거기서 시작할 수 있다.
- **`invokedynamic` 실행 0** — 부트스트랩 호출·`MethodHandle` 결정·콜사이트 링크 전부 미착수.
- **`ldc` 로 태그 15·16·17 을 싣는 경로 미지원** — `ConstantPoolReference::from_constant_pool`
  이 그 셋에 `None` 을 돌려주므로 그런 클래스는 **여전히 `Malformed`** 다. 오늘 픽스처가
  그 경로를 타지 않고(javac 의 문자열 연결은 `ldc` 로 핸들을 싣지 않는다) 별 축이다.
- 태그 **16·17 은 실행 픽스처가 없다** — 단위 테스트로만 덮인다. javac 가 그 둘을 내는
  평범한 코드를 찾지 못했다(문자열 연결은 15·18 만 낸다).
