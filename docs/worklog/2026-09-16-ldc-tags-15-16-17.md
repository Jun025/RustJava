# 2026-09-16 — `ldc` of the method-handle family: "corrupt" → "not implemented"

Ticket: `rustjava-ldc-tags-15-16-17-still-malformed`. Successor to
`rustjava-cp-tags-15-18-parse-and-honest-diagnosis` (PR #43), which closed the same lie one
square over (`invokedynamic`) and pointed at this one in `STATE.md` ④-2.

## ⓪ The investigation came first, and it split in two

The ticket ordered the measurement before the fix, and the answer is not a single word.

### ⓪-1 The defect reproduces

The four positive fixtures, run end to end through `run_class` on the tree at `origin/main`
(`ab872b71`). The two negative controls are in ② below; all six were `ClassFormatError` before.

| fixture | before |
|---|---|
| `LdcMethodHandle` (`ldc` of tag 15) | `java.lang.ClassFormatError: Invalid class file` |
| `LdcMethodType` (`ldc` of tag 16) | `java.lang.ClassFormatError: Invalid class file` |
| `LdcDynamic` (`ldc` of tag 17) | `java.lang.ClassFormatError: Invalid class file` |
| `Ldc2WDynamic` (`ldc2_w` of tag 17) | `java.lang.ClassFormatError: Invalid class file` |

**OpenJDK 26.0.1 loads and runs all four without complaint.** That is what makes the sentence a
lie rather than a limitation — these are files this runtime cannot *do*, not files it cannot
*read*. Ground truth, `Class.forName` on each:

```
LdcMethodHandle -> loaded OK
LdcMethodType   -> loaded OK
LdcDynamic      -> loaded OK
Ldc2WDynamic    -> loaded OK
```

### ⓪-2 javac does not produce it — measured, not assumed

The ticket asked whether ordinary Java source reaches this code path. **It does not**, and the
search went as far as this machine allows:

1. **The JDK's own class files** — every `.jmod` of OpenJDK 26 (`java.base` and 27 others):
   **27,902 classes, 1,252,714 `ldc`/`ldc_w`/`ldc2_w` sites, zero** naming a tag 15/16/17 entry.
   The scanner is not vacuous: over the same corpus it resolved operands to
   `String 1,176,232 · Integer 23,292 · Long 20,006 · Float 12,909 · Class 11,991 · Double 4,791`,
   and **3,493 operands that no `ldc` can legally take** (tags 1/9/10/11/12 and out-of-range
   indices) — decode drift, which bounds the walker's error at **0.28%**, far under any rate
   that could hide 15/16/17 entirely.
2. **Targeted source shapes**, compiled at `--release 21`, `25`, and `26 --enable-preview`:
   string concat, lambdas, method references, records, sealed-interface switches, enum switches,
   pattern switches, `List.of`, text blocks, try-with-resources, asserts, comparator chains,
   anonymous classes, varargs. Tags 15/16/18 appear **only as bootstrap-method arguments** of an
   `invokedynamic` entry — never as an `ldc` operand. Tag 17 never appears at all.
3. **This repository's own `test-data/`** — 127 classes, 500 `ldc` sites, zero.

No third-party jar corpus (ASM/Kotlin/Scala output, where condy does occur) exists on this
machine: `find` over `$HOME`, `~/.m2`, `~/.gradle`, `~/.ivy2`, `~/Library/Caches` and
`/opt/homebrew/Cellar` returned **0 jars**. So the honest boundary is: *javac emits none; whether
some bytecode generator in the wild does was not measurable here.*

**Conclusion: the fixtures are synthetic, and that is stated in the generator, in the test, and
here.** They are not "what javac emits" and must not be described that way.

### ⓪-3 Why "synthetic" is still worth fixing

The previous round's fix was worth it because `"a" + args.length` reaches it. This one is not
reachable from javac. It is worth doing anyway for one reason, and the reason should be stated
plainly rather than dressed up: **the three constants are exactly the constants `invokedynamic`
support will need**, and STATE ④-1 already names that as the next big piece. Leaving `ldc` of
them reporting "corrupt file" means the first person to hand this runtime a hand-built or
ASM-built class gets a diagnosis that sends them to look for a disk error. Cost: +40/-3 lines of non-test
code across three files, about half of it comments.

## ① The fix

Same shape as the previous round — *parse it, then refuse it in the verifier* — because that is
where the precedent is and inventing a second idiom for the same problem is how a codebase grows
two of everything.

- `classfile/src/constant_pool.rs` — three payload-free `ConstantPoolReference` variants
  (`MethodHandle`, `MethodType`, `Dynamic`) and their `from_constant_pool` arms. **No operands are
  carried.** Resolving a method handle needs machinery that does not exist; the only consumer is
  the verifier, which turns them into a message. Shape is already checked by
  `validation::validate_constant_pool` (reference kind vs. target, descriptor well-formedness),
  which the previous round added, so nothing is resolved twice.
- `classfile/src/opcode.rs` — `0x12`/`0x13` accept all three; **`0x14` accepts only `Dynamic`**.
  JVMS 6.5 puts long/double(-typed) constants on the wide side, so a `MethodType` under `ldc2_w`
  is a corrupt file and stays one. That split is not decoration: it is negative control M4.
- `jvm-bytecode/src/verifier.rs` — one new arm, `UnsupportedFeature("ldc of a …")`. The existing
  `Opcode::Invokedynamic(_)` line is **untouched** (ticket ③).

After:

```
LdcMethodHandle -> java.lang.UnsupportedOperationException: Unsupported class file feature: ldc of a method handle
LdcMethodType   -> java.lang.UnsupportedOperationException: Unsupported class file feature: ldc of a method type
LdcDynamic      -> java.lang.UnsupportedOperationException: Unsupported class file feature: ldc of a dynamically-computed constant
Ldc2WDynamic    -> java.lang.UnsupportedOperationException: Unsupported class file feature: ldc of a dynamically-computed constant
```

## ② The price, and the proof it was not paid

Making `Malformed` disappear risks silencing genuinely broken files. Two fixtures exist for that
direction alone, and both still report `ClassFormatError`:

| negative control | why it must stay corrupt | OpenJDK 26 agrees |
|---|---|---|
| `Ldc2WMethodType` | JVMS 6.5: `ldc2_w` takes only wide constants | `VerifyError: Illegal type at constant pool entry 9` |
| `LdcUnknownTag` | tag 19 (Module) cannot appear in a class file | `ClassFormatError: Unknown constant tag 19` |

(Our runtime answers `ClassFormatError` where OpenJDK answers `VerifyError` for the first one —
it rejects at parse time, earlier than the JVM's verification pass. Both say "this file is
wrong"; only the phylum differs, and nothing in this repo asserts the phylum.)

## Adversarial mutations — five, and one of them found a gap in my own test

Each applied to the fixed tree, then reverted.

| # | mutation | expected | result |
|---|---|---|---|
| M1 | remove the new verifier arm | host abort — `constant_to_value`'s `unimplemented!()` becomes reachable | **`panicked at jvm-bytecode/src/interpreter.rs:1063`** ✓ |
| M2 | `from_constant_pool` back to `None` for 15/16/17 | positives red | FAILED ✓ |
| M3 | `ldc` arms back to the old accept set | positives red | FAILED ✓ |
| M4 | let `ldc2_w` take a `MethodType` | negative control red | FAILED ✓ |
| M5 | make the constant-pool tag switch a pass-through | something red | FAILED — but **not by my test** |

**M1 is the one that matters.** It is the exact shape the previous round measured for
`todo!()` at `interpreter.rs:631`: remove the verifier guard and the failure stops being a guest
exception and becomes a host abort. The new verifier arm is load-bearing, and now measured to be.

**M5 is the honest finding.** Running M5 against only `--test test_class_format` came back
**all green** — my new `LdcUnknownTag` test did *not* catch a pass-through tag switch. It passes
for an adjacent reason (the mutation's hardcoded `descriptor_index: 0` fails validation), not
because it detects the tag. The axis *is* locked, by the previous round's unit test
`constant_pool::tests::tags_outside_the_accepted_set_are_still_rejected`, which goes red under
M5 — but it is locked one layer down from where I asserted it, and a reader of
`test_class_format.rs` alone would draw the wrong conclusion. Recorded rather than papered over.

## Fixtures

`test-data/ldc/*.class`, six files, generated by `test-data/src/ldc/make_ldc_fixtures.py`
(committed; `python3 test-data/src/ldc/make_ldc_fixtures.py` regenerates them byte for byte).
Written by hand rather than with `java.lang.classfile` for two reasons: the two negative controls
are *deliberately malformed* and no class-file builder API will construct them, and a committed
generator that needs no JDK keeps the fixtures reproducible on a machine without one.

Two details the real JVM taught, which a generator written from the spec alone would have got
wrong:

- **Tag 17 needs major ≥ 55.** At major 52 OpenJDK answers `ClassFormatError: Class file version
  does not support constant tag 17` — a *version* complaint that would have hidden the axis under
  test. `LdcDynamic`/`Ldc2WDynamic` are major 55; the rest are 52, matching the repo's others.
- **A `Dynamic` entry needs a real `BootstrapMethods` attribute** (JVMS 4.7.23). The first draft
  omitted it and OpenJDK said so. The fixtures now carry a genuine condy —
  `ConstantBootstraps.nullConstant` and `ConstantBootstraps.getStaticFinal` for `Long.MAX_VALUE`
  — which is why running them on a real JVM resolves cleanly instead of merely loading.

Our own `validation.rs` does not check either of those, which is *why* the divergence had to be
caught by running a real JVM rather than by reading our parser.
